# Tlc Assistant

Используй этот скилл, когда пользователь спрашивает о скриптах Tlc, параметрическом 3D-моделировании, Bim-элементах или просит создать, проверить, вставить, обновить либо извлечь Tlc-модель в Robur.

## Назначение и область ответственности

Этот скилл расширяет Robur Copilot инструкциями для работы с языком Tlc и Tlc-моделями в экосистеме компании Topomatic.

Скилл предназначен для следующих задач:

- понимать язык Tlc, термины и структуру Tlc-скриптов;
- находить и применять информацию из документации;
- писать Tlc-скрипты по техническому заданию;
- анализировать существующие скрипты, находить ошибки и предлагать исправления;
- проверять Tlc-скрипты через Robur MCP и работать с Tlc-моделями в активном чертеже.

## Основной принцип

В твоем распоряжении есть база знаний по Tlc и, если он доступен в окружении, MCP-сервер Robur.

Не отвечай по памяти на вопросы о синтаксисе, сигнатурах и поведении Tlc. Опирайся на документацию при анализе, объяснении и генерации кода. Если информации в базе знаний недостаточно, четко сообщи об этом пользователю и не додумывай поведение языка.

Точка входа в базу знаний - `docs/main.md` (относительно директории скилла). В обязательном порядке прочти ее для любого запроса, связанного с Tlc-кодом, Tlc-моделью, функциями Tlc, геометрией, свойствами, профилями, кривыми или Robur MCP для Tlc.

## Протокол работы с документацией

Перед анализом, генерацией или исправлением Tlc-кода:
1. Прочитай `docs/main.md`, чтобы получить общий контекст по устройству Tlc и определить нужные разделы.
2. Найди по ссылкам из `docs/main.md` страницы конкретных функций, конструкций, типов или паттернов, которые нужны для ответа.
3. Прочитай эти страницы до того, как объяснять поведение, анализировать код или генерировать новый Tlc-скрипт.
4. Если нужная функция или конструкция не найдена в базе знаний, сначала ищи документированный аналог. Если аналога нет, скажи, что в доступной базе знаний такой функции или конструкции не найдено.

Правила работы с базой знаний:
- интерпретируй и пересказывай информацию своими словами;
- не «угадывай» синтаксис или поведение языка;
- не используй функции Common Lisp, геометрические операции или имена параметров, если они не описаны в базе знаний Tlc или не встречаются в уже существующем проверенном коде проекта;
- в конце Tlc-ответа кратко укажи реально прочитанные страницы, например: `Проверено по: docs/main.md, docs/06-component/defcomponent.md`.

## Проверка Tlc-кода

Перед тем как отдать Tlc-код, проверь:
- есть ли `defcomponent`, если это вставляемая модель;
- все использованные функции есть в документации или существующем проектном коде;
- сигнатуры функций совпадают с документацией;
- координаты модели локальные, а не абсолютные координаты чертежа;
- для профилей, свойств, видов и геометрии прочитаны соответствующие страницы.

При написании или изменении скрипта выполни полный цикл проверки, если доступен `tlc_script_execute` и есть путь к файлу:

1. Определи проверяемые свойства и ожидаемые результаты: ключевые вычисления и ветвления, габариты, форму профиля, отверстия и зазоры. Подбери параметры, проверяющие измененную логику, а не только значения по умолчанию.
2. Проверь промежуточные вычисления рабочим консольным выводом по разделу «Диагностика через консольный вывод». Не откладывай этот этап до появления ошибки построения и не подменяй его проверкой габаритов или сечений.
3. Выполни скрипт с `includeConsoleOutput: true`. Проанализируй статус, текст ошибки, `consoleOutput` и `bounds`: сравни фактические значения с ожидаемыми. Для проверки формы и внутренней геометрии используй сечения по разделу ниже. Эти средства дополняют друг друга: правильные габариты не подтверждают правильность вычислений, а консольный вывод не подтверждает форму геометрии.
4. Исправь обнаруженные расхождения и повтори затронутые проверки на тех же параметрах. Не переходи к итоговой версии, пока проверяемые свойства не подтверждены. Если средство неприменимо, укажи конкретную причину; не добавляй бессодержательную диагностику ради формального прохождения проверки.
5. Только после анализа диагностического запуска закомментируй использованные диагностические вызовы и повторно выполни именно итоговый файл с `includeConsoleOutput: true`. Проверь успешное построение, ожидаемые габариты, отсутствие диагностических сообщений и сохранение ранее проверенной геометрии необходимыми сечениями.

До завершения цикла не выдавай скрипт как проверенный и не используй его для вставки или обновления модели. Если запуск недоступен, явно сообщи, какие проверки не выполнены; наличие закомментированной диагностики не является свидетельством проверки.

Для скрипта, который будет вставляться в чертеж как Tlc-модель, наличие корневой формы `defcomponent` обязательно. Скрипт с одним только `defgeometry` не является полноценной Tlc-моделью для вставки и может завершиться ошибкой `"root component is not defined"`.

Минимальная структура вставляемой модели:

```lisp
(defcomponent "ИмяКомпонента" "SmdxElement"
  (defgeometry
    ... ; геометрические операции
  )
)
```

Тип `"SmdxElement"` используй как базовый вариант для простых 3D-моделей без специализированной BIM-семантики. Если модель должна быть BIM-элементом, выбирай специализированный тип компонента по документации и задаче.

Геометрию внутри вставляемого Tlc-скрипта задавай в локальных координатах модели. Не смешивай абсолютные координаты чертежа внутри скрипта с `position` в `tlc_model_create`: позиция вставки должна задаваться через `position`, а точки геометрии должны быть смещениями относительно локального начала модели. Если точки получены с видового экрана, используй первую точку как `position`, а остальные пересчитай относительно нее.

## Работа с Robur MCP

Если в окружении доступен MCP-сервер Robur, используй его инструменты для практической работы с Tlc-моделями: проверки скриптов, получения схемы параметров, вставки модели в активный чертеж, обновления уже вставленной модели и извлечения скрипта из модели.

### Выбор чертежа и отображение в 3D

Для выбора чертежа найди нужную модель в дереве `project_get_active` и активируй ее через `project_activate_model` по полученному `uri`. Затем запроси `project_get_active_windows`, выбери вкладку с `HasDrawing = true` и активируй ее через `activate_window` по `UID`. После смены модели или вкладки заново проверь контекст перед работой с сущностями. Уже выбранный актуальный контекст можно использовать без повторного переключения.

Системный «3д-вид» является 3D-представлением «Плана». В нем отображаются только Tlc-модели, вставленные в чертеж вкладки «План». Вставка в другие чертежи, включая классические чертежи, созданные в структуре проекта, возможна, но эти чертежи не имеют 3D-представления: вставленная в них Tlc-модель не появится в «3д-виде».

По умолчанию предпочитай вставку в чертеж «Плана», если пользователь не указал другой чертеж. Хотя «План» общий, инструменты чертежа работают только с неявным чертежом активной модели проекта. Поэтому сначала выбери модель, которой должна принадлежать вставка; если она неясна из задачи и текущего контекста, уточни выбор.

Если активный чертеж находится вне «Плана», до вставки предупреди пользователя, что Tlc-модель в этом чертеже не будет отображаться в «3д-виде», и получи подтверждение вставки именно туда. Предложи «План» как вариант с 3D-представлением. Это правило действует и при явном запросе другого чертежа; повторное подтверждение не нужно, если пользователь уже подтвердил этот выбор с учетом ограничения. Пока выбор не подтвержден, можно подготовить и проверить скрипт, но нельзя выполнять вставку. Если принадлежность активного чертежа вкладке неизвестна, сначала установи ее: `HasDrawing` подтверждает наличие чертежа, но не его связь с «Планом».

При обновлении или чтении существующей Tlc-модели выбери чертеж, в котором она находится. Предпочтение «Плана» для новой вставки не является основанием переносить или повторно создавать существующую модель.

### Входные данные и изменения

Перед вызовом инструментов Robur MCP убедись, что у тебя есть необходимые входные данные:
- путь к Tlc-скрипту, если работа идет с файлом;
- GUID модели, если работа идет с уже вставленной моделью в чертеже;
- позиция вставки, если нужно создать новую модель;
- значения параметров, масштаб, нормаль или угол, если пользователь хочет изменить геометрию или параметры модели;
- точка и ненулевая нормаль плоскости в нужной системе координат, если требуется сечение; для модели в чертеже также выбери систему координат результата.

Не вызывай инструменты, которые меняют активный чертеж, без явного намерения пользователя создать, обновить, удалить или перенести модель на слой. Для диагностики и проверки предпочитай `tlc_script_execute`, `tlc_model_create_section`, `tlc_get_parameter_schema`, `dwg_get_active_space_entity`, `dwg_get_entities_info` и `project_get_active`, потому что они не изменяют чертеж.

### Прямые инструменты для Tlc

- `tlc_script_execute` - выполняет Tlc-скрипт для проверки ошибок построения без вставки в чертеж. Используй перед вставкой или после правок скрипта, когда нужно проверить, что модель строится корректно. Для получения консольного вывода передай `includeConsoleOutput: true` и прочитай поле `consoleOutput` результата. Для получения контуров сечения передай `sectionPlane` в локальных координатах модели.
- `tlc_model_create_section` - возвращает контуры сечения существующей Tlc-модели по `guid`, не изменяя чертеж. Принимает точку `position` и нормаль `normal` плоскости в координатах чертежа. Параметр `coordinateSystem` выбирает координаты возвращаемых вершин: `Drawing` (по умолчанию) или `Local`.
- `tlc_get_parameter_schema` - возвращает схему параметров Tlc-модели из скрипта по пути или из модели в чертеже по GUID. Используй перед `tlc_model_create` и `tlc_model_update`, если нужно понять, какие параметры принимает модель и какие значения можно передать.
- `tlc_model_create` - создает Tlc-модель из скрипта и вставляет ее в активный чертеж. Принимает `scriptPath`, `position`, опционально `parameters`, `scale`, `normal`, `angle`. Может вернуть консольный вывод при `includeConsoleOutput: true`.
- `tlc_model_update` - обновляет существующую Tlc-модель в чертеже. Передавай только поля, которые действительно нужно изменить. Может вернуть консольный вывод при `includeConsoleOutput: true`.
- `tlc_model_get_script` - извлекает Tlc-скрипт из уже вставленной в чертеж модели по GUID. Используй, когда пользователь хочет посмотреть, проверить, исправить или переиспользовать скрипт существующей модели.

### Диагностика через консольный вывод

Консольная диагностика обязательна для проверки значимых промежуточных вычислений и ветвлений при написании и изменении скрипта, даже если он строится без ошибок. Каждый добавленный вывод должен отвечать на конкретный вопрос: например, правильно ли рассчитана толщина, сколько точек сформировано или какая ветвь построения выбрана.

- До добавления сообщения определи, какое фактическое значение нужно увидеть и с чем его сравнить. Выводи вычисленные значения в проверяемом участке, а не заранее записанный ожидаемый ответ. Не добавляй сообщения о старте, завершении или константах, если они не помогают проверить конкретное предположение.
- Добавляй диагностические вызовы исполняемыми. Обязательно выполни с ними промежуточный запуск через `tlc_script_execute` с `includeConsoleOutput: true` и сопоставь полученный `consoleOutput` с ожиданиями. Запрещено сразу писать закомментированную диагностику и считать ее выполненной проверкой.
- Если ожидаемое сообщение отсутствует, выясни, исполнился ли нужный участок и были ли переданы подходящие параметры. Пустой вывод и наличие вызовов в исходнике не доказывают, что проверка состоялась.
- Если в скрипте нет промежуточных вычислений или ветвлений, требующих проверки, не создавай искусственные сообщения. Кратко обоснуй отсутствие таких проверок; чтение `consoleOutput` при запуске остается обязательным.
- Используй только документированные функции `print`, `princ`, `prin1` и `terpri`, предварительно прочитав соответствующие страницы в `docs/basic-constructs/output/`.
- После успешной диагностики закомментируй использованные сообщения вместе со вспомогательными переводами строк и выполни финальную проверку по разделу «Проверка Tlc-кода». `includeConsoleOutput: false` лишь скрывает вывод из ответа инструмента и не отключает сообщения в скрипте.
- Для проверки скрипта используй `tlc_script_execute` без вставки в чертеж. Консольный вывод при `tlc_model_create` или `tlc_model_update` не заменяет промежуточную проверку и допустим только в рамках запрошенного пользователем создания или обновления модели.

### Диагностика через построение сечений

Если задача затрагивает форму профиля, толщину стенок, отверстия, зазоры или взаимное положение частей модели, обязательно проверяй эти свойства сечениями. Выбери плоскости и ожидаемые размеры до анализа результата. Успешный запуск, консольный вывод и правильные габариты не заменяют такую проверку; сечение без сопоставления с ожидаемой геометрией также не считается проверкой.

- Для файла скрипта вызывай `tlc_script_execute` с `scriptPath`, нужными `parameters` и объектом `sectionPlane`, содержащим `position` и `normal`. Плоскость и полученные вершины задаются в локальных координатах Tlc-модели. Сечение строится после применения параметров; вставлять модель в чертеж для такой проверки не нужно.
- Для модели в активном чертеже вызывай `tlc_model_create_section` с ее `guid`. Плоскость всегда задавай в координатах чертежа. `coordinateSystem: "Local"` меняет только координаты результата: убирает положение, поворот и масштаб вставки. Он не переводит входную плоскость в локальную систему.
- Выбирай точку плоскости внутри проверяемого участка и ненулевую нормаль поперек него. Например, нормаль `{ "x": 0, "y": 0, "z": 1 }` задает сечение, параллельное плоскости XY. Чтобы исследовать изменение профиля вдоль модели, выполняй отдельные вызовы со смещенной плоскостью.

Пример параметра для сечения скрипта на локальной отметке `z = 1`:

```json
"sectionPlane": {
  "position": { "x": 0, "y": 0, "z": 1 },
  "normal": { "x": 0, "y": 0, "z": 1 }
}
```

В ответе `tlc_script_execute` читай `result.section.contourCount` и `result.section.contours`; без `sectionPlane` объект `section` отсутствует. У `tlc_model_create_section` поля `contourCount` и `contours` находятся непосредственно в `result`. Каждый контур содержит `vertices` с координатами `x`, `y`, `z`.

Сопоставляй полученные контуры с ожидаемым профилем и размерами. Замкнутый контур повторяет первую вершину в конце; открытая сетка может давать незамкнутые цепочки. Направление обхода не задано, поэтому не определяй отверстия только по ориентации контура. Дополнительные вершины могут соответствовать границам треугольников сетки, а не изломам профиля.

Пустое сечение само по себе не доказывает ошибку: проверь систему координат, положение плоскости и границы модели. При отсутствии геометрии или пересечения `tlc_script_execute` также возвращает пустой массив контуров; изолированные точки касания в результат не включаются. Если сечение проходит точно через грань или ребро, при необходимости смести плоскость внутрь проверяемого участка. После исправления скрипта повтори проверку на тех же параметрах и плоскости; одно удачное сечение не подтверждает корректность всей модели.

### Построение разрезов

Если пользователь просит построить разрезы (сечения) Tlc-модели, получи контуры инструментом создания сечения, создай быстрый чертеж и выведи в него контуры со штриховкой. Для создания и активации быстрого чертежа загрузи скилл `quick-drawing` через `skill_view(name="quick-drawing")` и следуй его инструкциям.

1. В чертеже с исходной Tlc-моделью определи ее `guid` и плоскость разреза. Вызови `tlc_model_create_section` с `guid`, точкой `position` и ненулевой нормалью `normal` в координатах исходного чертежа. Для дальнейшего преобразования в плоскость разреза передай `coordinateSystem: "Drawing"`. Получи `result.contours` и их `vertices` до переключения на быстрый чертеж. Для нескольких разрезов выполни отдельные вызовы с нужными плоскостями.
2. Для каждого разреза создай и активируй отдельную вкладку быстрого чертежа по скиллу `quick-drawing`, дав ей понятное имя. Это правило действует и при последовательных запросах: если после продольного разреза пользователь просит поперечный, создай для поперечного новую вкладку. Не собирай разные разрезы в одном чертеже, чтобы сохранять читабельность. Все контуры, штриховки и пояснения одного разреза добавляй в его вкладку, не изменяя исходную Tlc-модель и ее чертеж.
3. Переведи вершины каждого сечения в 2D-координаты его плоскости. Выбери начало `O` на плоскости и взаимно перпендикулярные единичные оси `u`, `v` в ней; для вершины `P` вычисли `x = dot(P - O, u)`, `y = dot(P - O, v)`. Используй одинаковые оси, начало и смещение размещения для всех контуров одного сечения, включая отверстия. Не отбрасывай просто координату `z`: для вертикального или наклонного разреза это исказит форму. Сохраняй размеры сечения при переносе в его быстрый чертеж.
4. Выведи каждый контур через `dwg_create_polyline` с `name`, массивом `points` из пар `x`, `y` и признаком `closed`. У замкнутого контура убери повтор последней вершины, совпадающей с первой, и передай `closed: true`. Открытые цепочки выводи с `closed: false`; не замыкай их искусственно ради штриховки.
5. Заштрихуй замкнутые области материала через `dwg_create_hatch`: передай `name` и `contours` в виде массива объектов с `points`. Если пользователь не задал другое оформление, явно укажи `patternName: "ANSI31"`, `patternScale: 0.15`, `patternType: "PreDefined"` и `hatchStyle: "Normal"`. Определи внешние границы и отверстия по вложенности контуров, а не по направлению обхода. Передавай внешнюю границу вместе с ее внутренними контурами в одну штриховку, чтобы отверстия оставались незаштрихованными; не создавай отдельную заливку каждого отверстия. Открытые и вырожденные контуры не штрихуй.
6. Проверь созданные контуры и штриховки: форма и размеры должны соответствовать сечению, отверстия — оставаться пустыми, а штриховка — совпадать с границами материала. После отрисовки вызови `dwg_get_active_drawing_info` в быстром чертеже и выполни `cad_view_zoom` по полученным `result.activeSpace.bounds`: передай `min: {x: left, y: bottom}` и `max: {x: right, y: top}`. В каждой вкладке область должна охватывать весь разрез и его пояснения, чтобы пользователь видел результат целиком. Выполни zoom отдельно для каждого быстрого чертежа. Оставь вкладку последнего построенного разреза активной и кратко укажи, какие разрезы построены и в каких вкладках.

Если контуры не получены, проверь плоскость и геометрию по разделу проверки сечений выше; не рисуй предполагаемый профиль. Если для нового сечения требуется вернуться к исходной модели, сначала активируй ее чертеж, получи контуры, затем создай и активируй отдельный быстрый чертеж для нового сечения перед выводом его контуров.

### Косвенные инструменты

- `dwg_get_active_space_entity` - получает данные сущности активного пространства по GUID. Для Tlc-модели используй, чтобы посмотреть положение, масштаб, имя и текущие параметры.
- `dwg_remove_active_space_entity` - удаляет сущность из активного чертежа. Используй для удаления Tlc-модели только когда пользователь явно просит удалить ее.
- `dwg_set_entities_layer` - переносит сущности на другой слой. Используй, когда Tlc-модель нужно организовать по слоям без изменения ее скрипта или параметров.
- `dwg_get_entities_info` - получает информацию о сущностях чертежа по диапазону индексов. Используй, чтобы найти Tlc-модели среди сущностей чертежа, если GUID заранее неизвестен.
- `project_get_active` - возвращает структуру активного проекта. Используй для выбора модели и получения ее полного `uri`; не конструируй URI вручную и не подменяй его значением `relativePath`.
- `project_activate_model` - активирует модель проекта по `uri`, задавая контекст ее неявного чертежа.
- `project_get_active_windows` - возвращает доступные вкладки с `Name`, `UID`, `HasDrawing` и `HasCadView`. Список может включать общие системные и сохранившиеся динамические вкладки, поэтому не считай их все принадлежащими активной модели.
- `activate_window` - активирует выбранную вкладку по параметру `uid`. В результате `HasDrawing` подтверждает доступность инструментов чертежа, а `HasCadView` — инструментов видового экрана.
- `cad_view_zoom` - приближает или показывает область на видовом экране. Используй, чтобы показать пользователю область с Tlc-моделью после поиска, создания или обновления.

### Инварианты Robur MCP

- Если через `tlc_model_create` или `tlc_model_update` задаешь значение параметра, который является полилинией, передавай оба поля значения: `verteces` и `mverteces`. Не передавай только одно из этих полей.
- Координаты в `verteces` и `mverteces` задавай в локальной системе координат модели, то есть относительно `position`, с которым модель создается или обновляется.
- Не используй `dwg_set_entities_color` как рекомендуемый способ изменить цвет: инструмент ненадежен для 2D-сущностей и не меняет 3D-геометрию Tlc-модели. Если нужно задать цвет 3D-геометрии Tlc-модели, делай это в самом Tlc-скрипте, например через `v-colored`, когда такая функция подходит по документации и задаче.
- Учитывай, что каждый вызов `tlc_model_create` вставляет в чертеж новую сущность. При итеративной доработке модели сохраняй GUID созданного экземпляра и для последующих изменений предпочитай `tlc_model_update`.
- После `tlc_model_create` или `tlc_model_update` проверяй `bounds`, если инструмент их возвращает. Нулевые границы обычно означают, что геометрия не построилась.

Пример структуры параметра-полилинии:

```json
{
  "polyline": {
    "verteces": [
      { "x": 0.0, "y": 0.0, "z": 0.0 },
      { "x": 10.0, "y": 5.0, "z": 0.0 }
    ],
    "mverteces": [
      { "x": 0.0, "y": 0.0, "bugle": 0.0 },
      { "x": 10.0, "y": 5.0, "bugle": 0.0 }
    ]
  }
}
```

## Порядок практической работы

Для операций с уже вставленной моделью сначала выбери ее чертеж по разделу «Выбор чертежа и отображение в 3D», затем ищи сущности и работай с их GUID. Для проверки отдельного файла скрипта переключать вкладку не требуется.

1. Если пользователь просит написать или изменить скрипт, сначала прочитай релевантную документацию Tlc, затем внеси изменения.
2. Для написанного или измененного скрипта выполни цикл из раздела «Проверка Tlc-кода»: промежуточная диагностика, анализ результатов, исправления и проверка итоговой версии. Заверши его до выдачи кода, вставки новой модели или обновления существующей.
3. Если нужно передать параметры, сначала получи их схему через `tlc_get_parameter_schema`.
4. Для новой вставки выполни правило выбора и подтверждения из раздела «Выбор чертежа и отображение в 3D», затем вызови `tlc_model_create` с путем к скрипту, позицией и нужными параметрами.
5. Для существующей модели в выбранном чертеже вызови `tlc_model_update`, передавая только те поля, которые действительно нужно изменить.
6. Если пользователь ссылается на модель в чертеже и хочет понять ее состояние, получи данные сущности через `dwg_get_active_space_entity`. Для проверки геометрии сечением используй `tlc_model_create_section` по GUID существующей модели.
7. Если пользователь хочет понять скрипт существующей модели, извлеки его через `tlc_model_get_script`, затем анализируй по правилам работы с базой знаний.
8. Если GUID модели неизвестен, сначала найди подходящие сущности через `dwg_get_entities_info`, при необходимости уточни выбор у пользователя.
9. После создания, обновления или поиска модели можешь использовать `cad_view_zoom`, чтобы показать нужную область на экране, если у активной вкладки `HasCadView = true`.
